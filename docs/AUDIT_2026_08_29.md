## 3. Что осталось нерешённым

1. **Keystore release-ключа** — владельцу: `keytool -genkeypair` + 4 секрета в GitHub (docs/RELEASE.md §1–2). Код полностью готов; без этого релиз физически не подписан.
2. **Секреты в Secret Manager** — env-подход сохранён (приемлемо для single-instance), миграция на External Secrets — владельческое инфра-решение.
3. **Бэкап-крон Postgres** — RPO/RTO и процедура описаны в RUNBOOK §4; сам cron на хосте — владельческое.
4. **UI-экран управления accessibility-списками** — движок (`AccessibilityPrivacyStore`) готов, осталось Compose-окно в Settings (нужна локальная сборка для проверки).
5. **Android-side latency-метрики** (STT/decision/local/cloud/TTS) — нужен on-device benchmark-цикл; в sandbox без устройства не проверить.
6. **Деплой Prometheus/Grafana** — конфиги готовы в `deploy/prometheus/`; фактическая установка на хост — владельческая.
7. **Ручное разрешение накопленных RECONCILIATION-заказов** — по RUNBOOK §5 (пока нет query-API провайдеров).

## 4. Что нельзя решить без Android/platform constraints (или без пересмотра решений)

- **Точный E2E-тест accessibility против банков/локскрина** — только на реальных устройствах (фрагментация вендоров, флаг isPassword не гарантирован).
- **Полное выделение чистой state-machine из VoiceInteractionOrchestrator** — требует рефакторинга 1040 строк с итеративной компиляцией и device-тестами; прототип показал, что «движок в стороне» дрейфует — это работа на 2–3 дня в среде со сборкой.
- **Апгрейд AGP/Kotlin/Compose до 2026-линий** — цепочка KSP/Hilt/Room/lombok-совместимости, требует локального `assembleDevDebug`+тестов после каждого шага.
- **Снятие single-instance** — отклонено спецификацией (§19), не техническая проблема.
- **Per-app automation Accessibility в фоне** — Android ограничивает a11y-сервисы (user warning, OEM-killers); программно не обходится.

## 5. Проблемы, перешедшие из архитектуры в product decisions

1. **Лицензия** — выбрана проприетарная (соответствует платному продукту); если владелец хочет OSS — заменить LICENSE (+README, NOTICE), решение одной правкой.
2. **UI управления privacy-списками** и его discoverability — продуктовый UX-вопрос.
3. **Квоты/цены провайдеров и `ExecutionPolicyConfig`** (сколько retries в проде) — экономика, не архитектура.
4. **Локальные модели (Gemma)** — продукт ещё не поставляет модель; strategy вокруг on-device AI — продуктовая.
5. **Именование/брендинг OMNIX vs JARVIS** — вне кода.

## 6. Следующий самый важный шаг

**Выпуск первого подписанного релиза:** владелец генерирует keystore по docs/RELEASE.md §1–2, запускает workflow «Release JARVIS (signed)» на staging, ставит AAB на устройство, проходит смоук (активация → голос → локальная команда → облачный запрос → screen reader на обычном и «банковском» приложении — последний обязан честно отказать). Это замыкает единственный недостающий физический элемент production-цепочки — всё остальное уже в main и покрыто CI.

Следующие инженерные шаги после релиза (в порядке важности):
1. Compose-экран управления accessibility-allow/block-листами.
2. Поднять Android coverage floor (24→35%) на новых тестах decision/tools.
3. Выделение чистой state-machine оркестратора (2–3 дня, среда со сборкой).
4. query-API провайдеров биллинга → автозакрытие RECONCILIATION.
5. Зависимости 2026-линий (агп/котлин) по одному шагу с прогоном CI.
