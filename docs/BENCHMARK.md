# JARVIS Benchmark v1 — Baseline (Этап 4)

**Итог: routing accuracy = 73.0% (73/100).** Это честный baseline, не цель.
Benchmark нашёл 27 неверных маршрутов, включая несколько реальных багов
production-кода.

Артефакты: [`docs/benchmark/`](benchmark/) — `benchmark-report.txt`,
`benchmark-results.json`, `benchmark-results.csv`.

---

## 1. Как запустить

```bash
./gradlew :app:testDebugUnitTest --tests '*BenchmarkRunnerTest*'
# артефакты: app/build/benchmark/

# regression-гейт (быстрее, 1 прогон):
./gradlew :app:testDebugUnitTest --tests '*BenchmarkRegressionTest*'
```

## 2. Что именно измерялось

Прогон идёт через **настоящие** `FastCommandRouter`, `ExecutionDecisionEngine`,
`CognitivePlanner`, `AgentCognitiveLoop`, `ToolExecutor`, `OnDeviceLocalAi`.
Имитации маршрутизации нет.

Подменены только внешние границы, недоступные на JVM: нативный инференс
MediaPipe, сеть до провайдеров, Android-тулы.

### Ограничения (важно при чтении цифр)

| Что | Статус |
|---|---|
| Routing accuracy | **измерено на реальном коде** |
| Latency маршрутизации | измерена, но задержки инференса/сети синтетические |
| Local AI cold/warm | **симуляция** (реального GPU/NPU нет) |
| RAM / CPU / battery | **НЕ ИЗМЕРЕНО** — нужен физический Android |
| Стоимость облака | **UNKNOWN** — тарифов нет в конфигурации сервера |
| Provider latency / fallback | симуляция, один провайдер |
| Качество ответов | не оценивалось (только маршрут) |
| Датасет | **синтетический**, 100 команд, написан вручную |

Цифры latency ниже отражают **логику принятия решения**, а не реальную
производительность на устройстве.

## 3. Датасет

100 команд, ground truth зафиксирован **до** запуска, каждый кейс несёт
поле `rationale` — почему ожидается именно такой маршрут.

```
DEVICE 25 · LOCAL_AI 22 · CLOUD_AI 15 · CLOUD_WEB 10
AGENT 10 · AMBIGUOUS 6 · EDGE_CASE 7 · PRIVACY 5
```

Набор намеренно **не** подогнан под высокий процент Local AI: команд
устройству больше всего, как в реальном использовании ассистента.

## 5. Топ-10 проблем

### 1. CLOUD_AI: 0/15 — критично

Ни один сложный аналитический запрос не ушёл в облако. Причина: у движка
**нет понятия «сложность запроса»**. Локальная модель (Gemma 3 1B) берёт
всё, что короче 1200 символов, включая юридический анализ и генерацию кода.

Из 15 кейсов: 12 → LOCAL_AI, 2 → AGENT, 2 → DEVICE_TOOL (см. п. 2).

**Влияние:** пользователь получает ответ 1B-модели там, где нужна 70B.
Тихая деградация качества — заметить её без benchmark невозможно.

### 2. AMBIGUOUS: 0/6 — нет механизма уточнения

«Открой», «Найди это», «Проверь» → LOCAL_AI генерирует ответ вместо вопроса
«что именно открыть?». В системе **вообще нет** пути CLARIFICATION.

`ExecutionResult.ConfirmationRequired` существует, но используется только для
подтверждения опасных действий, не для нехватки контекста.

### 3. Слово «следующий» перехватывает media.control — реальный баг

```
"Когда следующий матч сборной?"  → media.control (NEXT_TRACK)
"Проанализируй следующий договор…" → media.control (NEXT_TRACK)
```

`MediaIntentParser` матчит подстроку «следующий» без учёта контекста.
Проверено напрямую: `MediaIntentParser.parse("следующий") == NEXT_TRACK`.

**Влияние:** любой вопрос со словом «следующий» переключает музыку.
Это device false positive — самый опасный класс ошибок.

### 4. Слово «интернет» перехватывает device.wifi — реальный баг

```
"Найди в интернете информацию о моём диагнозе" → device.wifi
```

Секция 13 роутера ловит `q.contains("интернет")`. Хуже того: это был
**SENSITIVE**-запрос, то есть приватный запрос превратился в действие
с устройством вместо отказа.

### 5. Приоритет DEVICE выше приоритета приватности

`PRIV-005` (SENSITIVE + requiresWeb) ожидался как REFUSAL, но роутер
уверенно распознал «интернет» и выполнил device-команду до того, как
движок дошёл до проверки приватности.

Приватность проверяется только на облачном пути (`runCloud`). Device-путь
её не проверяет вовсе.

### 6. Пустой запрос не отклоняется движком

`EDGE-001` («») ожидался REFUSAL → получен CLOUD_AI. `FastCommandRouter`
возвращает `ForwardToLlm`, `OnDeviceLocalAi` отклоняет пустой текст как
`Unsupported`, и запрос уходит в облако вместо честного отказа.

Валидация есть на сервере (Этап 3), но клиент тратит сетевой вызов зря.

### 7. ScenarioMatcher ловит «отчёт»/«состояние» → ложный AGENT

```
"Сделай подробное резюме этого технического отчёта…" → AGENT (DIAGNOSTICS)
"Проанализируй финансовую отчётность…"               → AGENT (DIAGNOSTICS)
```

Ключевые слова `отчёт`, `состояние`, `статус` матчатся подстрокой, поэтому
аналитический запрос запускает диагностику устройства.

### 8. «Подготовь телефон ко сну» НЕ распознан как AGENT

`AGENT-001` → LOCAL_AI. При этом `ScenarioMatcher` содержит ключи `сон`,
`спать`, `ночной режим`, но фраза «ко сну» их не содержит («сну» ≠ «сон»).
Отсутствует лемматизация.

### 9. «Включи режим экономии заряда» → system.battery вместо AGENT

Роутер (секция 6, «заряд») срабатывает раньше, чем планировщик успевает
построить сценарий POWER_SAVING. Пользователь получает «заряд 80%» вместо
включения энергосбережения.

### 10. Произвольное многошаговое планирование отсутствует

`AGENT-009/010` («план поездки», «сравни 10 ноутбуков») не распознаются:
`ScenarioMatcher` знает только 10 предопределённых сценариев. Помечено в
датасете как `knownGap` заранее — benchmark это подтвердил.

---

## 6. Что НЕ сломано

Benchmark подтвердил и сильные стороны:

- **DEVICE 100%** — быстрый путь работает идеально, p50 = 13 мс;
- **LOCAL_AI 100%** — знаниевые вопросы корректно остаются на устройстве;
- **Unnecessary Cloud = 0%** — лишних облачных вызовов нет;
- **Cloud ratio 12%** — большая часть работы выполняется без сети;
- **PRIVATE/SENSITIVE ни разу не ушли в облако** (инвариант в regression-тесте).

исправлениями.

## 8. Рекомендации на Этап 5

По убыванию влияния:

1. **Классификатор сложности** для CLOUD_AI (проблемы 1) — сейчас 15%
   датасета маршрутизируется неверно.
2. **Границы слов вместо `contains`** в `MediaIntentParser`, секции Wi-Fi
   и `ScenarioMatcher` (проблемы 3, 4, 7, 9) — устранит device false positives.
3. **Путь CLARIFICATION** (проблема 2).
4. **Privacy-проверка до device-пути** (проблема 5).
5. **Замер на реальном устройстве**: battery, RAM, CPU, thermal — без этого
   пригодность Gemma 3 1B для длительной работы не доказана.
6. **Тарифы провайдеров в конфигурацию сервера** — тогда benchmark посчитает
   реальную стоимость вместо `UNKNOWN`.
